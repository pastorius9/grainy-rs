# Grainy Rust workspace review

Review branch: `port/review`. Starting revision: `9617c12e`. Reviewed all 29 crates, prioritising application and filesystem boundaries, updater/HTTP, monitor FFI, MCP, and background work. Thirteen application/library fixes and one test portability fix are included. Six remaining risks are recorded explicitly below; this is not a claim that every operation survives arbitrary process or power failure.

## Review coverage and compatibility

- Read the monitor module's unsafe blocks: UTF-16 termination and buffer capacity, bounded allocation/retry, owned DC deletion including `Drop`, extended monitor structure size and handle error cases. No unsafe change was needed. Scripted oracle cases and the existing read-only Windows monitor smoke test remain in the suite. This is not a driver audit.
- Reviewed catalogue transactions/WAL, SQLite backup and restore validation, staged Lightroom import/rollback, copy verification, file move/trash ordering, settings, sidecars and exclusive output creation. The crash and concurrency limits above remain material.
- Feedback retains its explicit-send flow and existing payload fields; no feedback was sent. Update verification still checks the downloaded byte count and SHA-256, validates archive paths/layout, and passes only the verified staged installer to the normal UI launch flow. No installer was run. Redirects may reach HTTPS asset hosting after the repository-qualified initial URL.
- MCP binds loopback, requires the bearer token, checks Host/Origin and bounds request size/connections. Authorised tools intentionally reach user-selected photo folders outside the catalogue; this is not a filesystem sandbox. Maintenance and Python-root checks were tightened without changing tool schemas.
- Reviewed worker/job mutex ordering, cancellation and reply application. The new generation boundary fixes the demonstrated catalogue-switch bugs. This does not prove every modal callback or every possible event ordering safe.
- Screened the remaining numerical, codec, engine, CLI, GPU, RAW and support crates and ran their existing tests. No pixel mathematics, dtype, operation order, golden tolerance, public name or runtime dependency changed. This was a risk-prioritised review, not a line-by-line formal verification or native-library fuzz campaign.
- Oracle source was read only. Relevant comparisons included `library.py` sidecar/file operations, `preferences.py`, `app.py` folder enumeration, `mcp_service.py` maintenance and `updater.py`. Python's newline/serialization quirks and legacy updater entry points stay intact. Unique XMP staging, Rust-only update trust and offline restrictions deliberately harden exceptional/system behaviour under this brief; they do not change normal photo results.

Dependencies added: **none**. XMP staging uses `tempfile`, already a runtime dependency of `grainy-library`. No unsafe code added. Possible shared follow-ups: one protected-output policy, a reusable existing-ancestor path resolver, and a portable exclusive atomic publication/move abstraction. No changes to `grainy-core` or `grainy-testkit`.

The additional file syncs can increase save/copy latency on slow storage. Initial thumbnail publication and app thumbnail rebuilds now share a process-local lock, so separate libraries can wait for each other's thumbnail work; this tradeoff was not benchmarked. Filesystem race and power-loss guarantees are limited as described in R14, R15 and R18.
