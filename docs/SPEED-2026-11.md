# Editing latency on two 24 MP RAW files

With GPU preview enabled and the Windows sRGB monitor profile active, the exposure slider was texture-ready in **42.1 / 21.9 ms** (Sony / Nikon). The separately fenced offscreen GPU draw completed in **24.1 / 26.4 ms**. Prepared Auto Tone took **63.4 / 37.7 ms**. Zoomed exposure release was **10.3× / 22.2×** faster. The full-resolution frame still takes longer than the fit frame.

## Measurement

Measured on 2026-11-20 on Windows 11, i9-12900K, RTX 3070, release profile with thin LTO. Inputs were the CC0 Sony A7 III `Sony_ILCE-7M3__DSC0009.ARW` and Nikon Z 6 `Nikon_Z-6_DSC_0754.NEF`. Fit uses the 2048-pixel long side, analysis uses 1800, and full uses the oriented original dimensions. The monitor was the Windows `sRGB Color Space Profile.icm` installed in the system colour directory. “GPU on” means the application preference is enabled. The worker chooses the path for the specific frame.

Timing tables report milliseconds. Paired entries mean **before → after**. The baseline was the implementation at `0175fd0e` plus the timing-only changes in `4206cbed`. For the additional button/slider/draw comparisons, the same diagnostic was built against an archived copy of those baseline sources inside this worktree’s ignored `target` directory. Runs used local files, an in-memory editing session and the system’s existing workload. Cold here means a newly constructed worker and empty application caches. Filesystem and driver caches were left alone.

Each camera/configuration was run three times, serially. The tables give the median of the three run medians. Each run used five edits for fit and warm direct development, three full-resolution releases, seven exposure edits for fenced drawing, and one opening or first click. The extra Auto Colour and negative remeasurement cases used three clicks per run. `GRAINY_TIMING=1` was enabled on both revisions. A click ends when the registered job applies its settings. A slider time begins with the real edit, traverses the worker, histogram, clipping and egui texture preparation and ends when the frame is accepted. The additional presentation test uploads the photo through egui-wgpu, samples it into a 1600 × 1000 target and waits for GPU completion. Monitor scan-out and desktop refresh are outside both endpoints.

## What changed the latency

- The old worker requested an sRGB development for its histogram and another development for the monitor. An ICC request selected the CPU reference and cleared the GPU resident image. In the revised worker, the histogram and clipping describe sRGB from one working image. The monitor receives that same image through its own output transform. ProPhoto and ICC receive canonical CPU floats because a small GPU rounding difference can cross a LittleCMS lookup boundary. HDR keeps its original presentation branch.
- For an otherwise neutral linear source in sRGB, exposure, contrast, white balance, whites and blacks are channel-independent. The CPU evaluates the original tone function at 32,769 interval endpoints. Only intervals with one possible display byte, histogram byte and clipping decision can use the table. Ambiguous pixels and out-of-range values use the original functions. For eligible RGB matrix/shaper monitor profiles, LittleCMS evaluates the corner bounds across all three inputs. Other monitors use the complete LittleCMS transform. Changes to geometry, camera-native development, film, local edits or another active processing stage use regular development. This shortcut is display-only.
- The original fit GPU upload on the first Sony exposure sequence took 15.3 ms. On the five subsequent frames the CPU spent 2.5–10.0 ms recording/submitting the resident prefix, 109.4–122.3 ms in the map/fence wait and 7.8–19.3 ms copying mapped floats. The wait includes queued compute, GPU transfer and synchronization. It cannot be assigned entirely to transfer bandwidth. The 2048-pixel working frame is about 32 MiB of RGB float32. Pipelines are built during device creation. Bind groups and parameter buffers are made for individual dispatches. With no masks, the old readback had a single owner, so the `Arc::try_unwrap` clone fallback did not explain the slowdown. The measured host local/clip tail was 2.0–5.4 ms.
- Neutral GPU colour, detail and finish stages now reuse the preceding buffer. Where the resident result already includes the final clip and no masks or output conversion remain, the worker can use the readback directly. The resident geometry survives an intervening ICC call. Fit and full retain separate stage caches. Initial GPU creation is deferred until an edit can actually use it. The Basic shortcut chooses CPU even with the GPU preference enabled. Other supported sRGB edits with no monitor transform can still use the GPU.
- Visible RAW decoding hands off the identical *pre-resize* half-size RGB or camera-native source for compatible image dimensions. The analysis job resizes it directly to 1800 with the original resize routine. It never resizes the 2048 preview. Other sources use the original 1800 loader. Preparation starts after the first accepted picture, on a separate pool capped at four threads. Concurrent clicks join it. The cache key includes the path, working space and effective RAW decoding mode. A change to native/DCP/negative mode that changes the decode requires another source. Switching documents cancels pending preparation and detaches its slot. An already-running native unpack can finish in the background.
- Slider edits are submitted at the end of the same UI frame. One dirty drag request may finish while newer values accumulate, then the newest value is submitted. The worker wakes egui on completion. Release, photo, crop and display changes supersede stale requests. Opaque photo textures take egui’s premultiplied upload path. Translucent frames retain their original conversion. Panning only changes the view. A zoom release still develops the full photo, with its decoded source and stages retained independently of drag-resolution work.

## Pixel and cache verification

- On each CC0 RAW, the 1800-pixel RGB values from the shared decode equalled an independent load for both ordinary and native/negative decoding. Auto Tone returned the same settings *and* measurement report. Maximum source difference was **0**.
- With the real Windows monitor profile, both RAWs had **0** maximum difference in any RGBA8 channel against CPU development plus full LittleCMS for successive exposure, temperature, blacks and shadows edits. Every clipping mask, channel flag and histogram bin matched. The generated tests also exercise byte boundaries, float edges, extreme exposure, a perturbed matrix/shaper profile, wide values and fallback eligibility.
- The existing 139-case GPU engine matrix ran on the RTX 3070. Maximum absolute float differences were **4.381e-6** for masks, **4.075e-6** for detail, **1.013e-6** for tone/colour/other, **5.364e-7** for geometry, **1.788e-7** for negatives, and **1.192e-7** for camera RAW. Both CPU fallback groups were bit-identical. The largest difference came from `mask_detail`. All existing per-case limits passed.
- Regression tests exercise cache invalidation across photos and effective load settings, a simultaneous prepare/click, one cold tone evaluation with a monitor, fit/full/fit reuse, resident GPU counters across ICC, stale drag results and panning without another request. Synthetic renderers cannot start background file reads. The name-dialog fixture holds the real worker’s completed reply until its historical pending-frame state is captured. The GPU output-pool test exercises non-neutral colour so it still checks more than 20 real buffer reuses, ordered readbacks and an outstanding clone. Its maximum float difference was 2.384e-7. Export still follows the original CPU arithmetic. The display-only shortcut is reached through the interactive worker.
- No dependencies were added. The branch diff contains zero golden or snapshot changes. No shared-crate follow-up is required.

## Reproduce

From the worktree root with Rust on PATH, build the diagnostic and give it one of the two CC0 RAW paths and the system monitor profile. `all` runs the direct engine, Auto Tone and worker matrix. `sliders`, `buttons`, `present` and `verify` run the additional checks.

```powershell
cargo build --release -p grainy-app --example preview_bench
$raw = '<folder of CC0 RAW samples>\Sony_ILCE-7M3__DSC0009.ARW'
$icc = 'C:\Windows\System32\spool\drivers\color\sRGB Color Space Profile.icm'
$env:GRAINY_TIMING = '1'
foreach ($case in 'all', 'sliders', 'buttons', 'present', 'verify') {
    & .\target\release\examples\preview_bench.exe $raw $icc $case
}
```
